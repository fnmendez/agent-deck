# Strict one-shot terminal send

`agent-deck session send FULL_SESSION_ID --strict-once --expected-thread NATIVE_THREAD_UUID --json --message-file -` reads the exact prompt from stdin. No prompt file is needed. This release supports the literal `claude` and `codex` tool types on macOS (Darwin) only. Other platforms return `refused`, `attempted: false`, `reason: "unsupported_platform"`; Linux native identity formats are intentionally not implemented. Other send modes are unchanged. Strict mode cannot be combined with `--no-wait`, `--defer-if-busy`, `--draft`, `--wait`, or `--stream`.

Strict mode refuses before terminal input unless the target has a fresh matching idle hook, a matching native thread anchor, an empty recognized composer with its visible cursor at the input position, raw terminal mode and bracketed paste enabled. A non-control-mode attached client active within the last 60 seconds, unknown client activity, copy mode, hidden cursor, vim mode, busy indicators, approval menus, unknown footers/placeholders, drafts and capture failures refuse. Claude requires its native `sessions/<pane-pid>.json` record with matching PID/sessionId, process start time (native `ps` reads use `TZ=UTC`, `LC_ALL=C`), Darwin PID domain, tmux identity and cwd; Codex requires the uncached tmux `CODEX_SESSION_ID` anchor plus an open CLI root rollout in the current descendant Codex process. Codex reads only the bounded first `session_meta` record, requires `source: "cli"` and `id == session_id == expected_thread`, and allows separate subagent rollouts without mistaking them for the main thread. Codex must be a running foreground TUI in the pane TTY/process group with the current native cwd matching the project; a background or suspended descendant cannot authorize a send. The unique main rollout must have a writable numeric FD with matching device and inode. Each pathname component is opened relative to a held nonsymlink directory; directory identities, root FD/access/device/inode, process ancestry and UTC start times are reread and must remain stable within and across proof calls. The verified root descriptor is held during revalidation. Missing or changed `ps`/`lsof`/FD evidence refuses. No account, model, session or runtime is changed.

The installed Codex0.153.4 main placeholder is recognized only as the exact `› Ask Codex to do anything` row with a BOLD, non-DIM marker, a DIM, non-BOLD placeholder, and cursor column2. Captures retain SGR style (`capture-pane -e`); RGB parameters containing2 are not confused with the DIM modifier. A typed copy of the same words refuses. A bare `›`, including an all-space draft with Home/cursor column2, is never positive evidence and refuses. Codex also requires exactly one complete measured footer ending in `Main [default]`; bare shortcuts, legacy context-only rows and missing/child labels cannot bypass it. Remote/backtracked `[Image #N]` rows also refuse: the native renderer can show its empty-text placeholder while such an attachment draft still exists. The measured full `gpt-6-astra … · Context N% used · … used · Fast … · Main [default]` footer is matched by an anchored grammar; extra text, other-agent labels and unknown menus refuse. The recorded fixture contains only the three safe lower rows. This proves the empty-text composer layout, not runtime idle, hook freshness or permission to send. A separate bounded observation found no image-attachment row near that composer; a later read found a busy hint. Live acceptance remains held, and the full busy/native/hook/client guards remain mandatory.

Source evidence is pinned to [Codex rust-v0.153.4 chatwidget](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/chatwidget.rs#L1996), [placeholder rendering](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/bottom_pane/chat_composer.rs#L4996), [status formatting](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/chatwidget/status_surfaces.rs#L711) and [main-agent label](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/app/thread_routing.rs#L136). This narrow recognition does not imply support for arbitrary provider versions or customized status lines.

Codex geometry is deliberately restricted to the measured **141 columns × 67 rows**, cursor `(2,64)` in zero-based coordinates, blank padding rows63/65 and the complete main footer at row66. The sender retains dimensions from both metadata samples and requires a full67-row capture; missing, cropped, shifted, resized or otherwise unsupported frames refuse. It never resizes a pane. This is a measured contract, not a claim that any screen above an arbitrary size is safe. Claude geometry was not broadened by this correction.

The pinned renderer explains why geometry is load-bearing. [ChatWidget](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/chatwidget/rendering.rs#L69) reserves BottomPane as non-flex with one top inset; [BottomPane](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/bottom_pane/mod.rs#L1953) reserves Composer as non-flex before other panels. [Flex allocation](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/render/renderable.rs#L302) gives non-flex children their requested space first. [Composer desired height](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/bottom_pane/chat_composer.rs#L4640) includes remote-image rows and their separator, not just text. For the supported normal-main layout with a one-row footer, nonempty images request their rows plus separator, textarea and padding; at the recorded67-row screen this gives visible image rows, or eliminates the textarea when images saturate its space. By contrast, a three-row composer rectangle leaves one textarea row, making `min(image_count, textarea_height-1)` zero: the four-row compact example can hide images behind the same styled placeholder. It is refused before staging. The source-derived fixture exercises the production capture/admission boundary with zero staging and zero submit.

The saved real fixture remains a **lower-region recording**, not a whole-pane or idle certificate. Tests reconstruct its measured global coordinates using synthetic blank history; actual private history was not captured into the fixture. Full capture, geometry, native idle, client and other guards remain required in production.

Claude's measured 2.1.260 bypass/status-line layout has a structural NBSP after `❯`. The additional recognition requires a complete frame, cursor column2, dividers immediately above/below the prompt, one nonempty custom-status row after the lower divider and the exact native hint `⏵⏵ bypass permissions on (shift+tab to cycle) · ← for agents` immediately after that status row. Only blank rows may follow the hint. These are relative positions, not a fixed screen size or cursor row: empty/SPACE+Home behavior was also tested in isolated 96×40 and 180×80 UIs. The observed director's 141×67 layout has prompt row62, status row64 and hint row65. Only the exact plain prompt `❯\u00a0` or `❯\u00a0 ` is recognized; there is no general whitespace normalization. The latter includes a possible software-cursor cell, and does not override the existing visible-cursor requirement.

An isolated installed-CLI UI test showed that empty input and ASCII spaces followed by Home can have identical raw prompt bytes and cursor position. In the measured bypass layout, every SPACE/NBSP/mixed whitespace draft loses ` · ← for agents` from the native hint, including after Home; deleting the test input restores it. That complete native hint is therefore mandatory. A mode-only/prefix hint refuses, and arbitrary words in the custom-status row never supply this evidence. Manual/default and other NBSP footer variants are unsupported. The recorded test data includes both bypass and manual whitespace cases; operative history/status is replaced by explicitly synthetic data in reconstructed tests. No model prompt was submitted during recording. Native identity, hook idle, client activity, modal, cursor-visibility, final-frame and no-replay gates remain required; no operative permission mode is changed.

The transport pins session ID, pane ID and pane PID, brackets each capture with metadata reads, rechecks native thread and idle status, then rechecks the active pane and composer immediately before one framed paste and one Enter in the same tmux command list. It refuses if the final snapshot is older than 500 ms at tmux invocation. This bounds observation age at invocation, not OS scheduling or tmux processing latency. It never presses Ctrl+C, Escape, clears/restores a draft, retries Enter or resends. Input must be valid UTF-8, nonempty and at most 64 KiB, with no control characters other than LF. Carriage returns are refused rather than normalized.

JSON fields are at the root:

- `delivery: "refused", attempted: false`: no terminal send was invoked. The queue may hold and retry after the refusal reason changes.
- `delivery: "unknown", attempted: true`: a terminal attempt was invoked. Never replay automatically. This remains unknown even with exit 0 and `success: true`; those only report that tmux accepted the command list. A transport error exits 1 with the same unknown outcome.
- `reason`, `session_id`, `expected_thread` identify the outcome and intended binding without echoing prompt or pane content.

The private tmux buffer is staged in server memory and cleaned up on all normal returns. Process termination may leave an unused named buffer; that is not delivery evidence. A caller crash, timeout or missing/malformed response must be treated as unknown, never as a safe refusal.

This is **not an atomic application enqueue**. The application can transition to a modal, start work, change threads or receive operator input after the final observation. tmux metadata/native anchors and hooks can lag; they are evidence, not a consumption acknowledgement. An async TUI may swallow the one Enter immediately following paste. If an operator starts typing after the final observation, the paste can still collide with their draft. These residual terminal races remain unknown and do not authorize rescue keys. Confirm consumption only from independently correlated native conversation events. No live send or runtime activation is covered by synthetic tests; the director owns that verification.
